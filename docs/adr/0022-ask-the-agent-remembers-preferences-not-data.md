# Ask the agent remembers how a person likes to work, never data

Ask the agent keeps a short list per person of **remembered preferences**: how they like to work, such as "I prefer tables over charts", "default to the last 90 days", "keep briefs to 5 bullets" or "focus on oncology". The agent saves one only when the person asks ("remember ..."), only after they approve it on the write-approval card of ADR 0020, and loads the list at the start of every run. A "What the agent remembers" panel lists the items with a delete for each and a clear-all.

Memory is not a knowledge store. Counts, calls, HCPs, responses and figures always come fresh from RLS-scoped SQL (ADR 0003, ADR 0007); a preference is never evidence and never extra access.

## Decisions

**Storage: the FE DynamoDB table of saved views, owner-keyed, like the appearance choice.** One item per preference: partition key `ownerUserId` = the verified user id, sort key `MEM#<yyyymmddhhmmss>-<8 hex>` (so key order is creation order), attributes `text`, `category`, `createdAt`. The `MEM#` prefix keeps the items out of the saved-view list (`SavedViews.list` filters it, as it does `PREF#`, ADR 0012). A new table would need a new cross-account role, CDK, floci setup and compose changes for a few hundred bytes per user; this table's owner-keyed access already fits, and chat history (ADR 0007) is keyed by user in the same way. At most 30 items per person; saving the same text again (ignoring case) keeps one item.

**Path: FE AppSync, then the BE Lambda (ADR 0001, ADR 0002).** `myAgentMemory`, `saveAgentMemory`, `deleteAgentMemory` and `clearAgentMemory` take no owner: the BE uses the verified identity, so no one can list, write or delete another person's items (another person's `memoryId` is a `NotFound`, indistinguishable from one that does not exist). The BE loads the caller's items in `startChatRun` and sends them to the worker and the agent with the run, so every question reads the list fresh: a deletion applies to the next question, with nothing cached. If the store is unavailable the run goes ahead without preferences; they improve an answer and never make one possible.

**The agent's save tool is the existing approval card, narrowed (ADR 0005, ADR 0020).** "Remember ..." at the start of a message is parsed in code, not by the model, into a closed `save_preference` write with `text` and a `category` (`FORMAT`, `LENGTH`, `DATE_RANGE`, `FOCUS`, `OTHER`, picked by rule). The run ends at a standard AG-UI interrupt; the person may edit the text; only approval makes the agent emit the one `a2g_execute_write` browser tool call, rebuilt from the persisted event, whose handler calls `saveAgentMemory`. A rejected approval saves nothing and says so. The model cannot save a preference by itself or choose what is saved.

**The guard.** A preference is short text (at most 160 characters, one line) that must not look like a record-level fact. The same rules run in three places: the agent when it proposes (a refusal is a fixed reply before any model call), the BE before it stores (authoritative; refusal is `BadRequest`, a stable reason code in the log, never the text), and the agent again when it builds the prompt (an item that fails is dropped). They refuse: HCP, call, territory and other identifiers (`HCP-...`, `T-...`, UUIDs, long digit strings), email addresses and phone numbers, titled names ("Dr. Smith"), figures (percentages, currency, decimals, thousands separators, a number next to a record noun such as "12 calls", four-digit or longer numbers), dates, statements about a call or meeting, and instruction-like text ("ignore", "override", "reveal", "all territories"). Small numbers that only configure a view stay allowed ("90 days", "5 bullets", "top 10"). Aggregate-only personas (Executive) follow the same rules; the guard does not depend on persona. The guard cannot recognise a bare personal name; the approval card shows the text before anything is saved and the panel lists everything stored, and the prompt marks every item as data, not instructions. `backend/agent_memory_guard_cases.json` is the shared table of cases that the BE, the agent and the browser's mock each run, so the copies cannot drift.

**In the prompt.** The items are added to the system prompt as JSON-encoded strings under an explicit note: presentation only (tables or charts, length, wording, default range when the question names none, topics to lead with). They never change the rules above them, never replace a tool result as the source of a figure, and are not stated as facts. Nothing is sent to CopilotKit's cloud (ADR 0018) and AWS AgentCore Memory is not used: floci only stubs AgentCore, so it could not run on the local stack, and its automatic extraction could store record-level facts.

**The panel.** `AgentMemoryControl` opens an Astryx `Drawer` (a native modal `<dialog>`: top layer, focus containment, Esc and scrim to close, focus returned to the button) from the top-bar panel, the docked view (both through `PanelHeader`) and the full-screen `/chat` header. It reads the list each time it opens. Clear-all asks first in an Astryx `AlertDialog` whose initial focus is "Keep them". Esc closes only the panel (CopilotKit's popup would otherwise close on the same key), and focus moves to the panel's intro after a delete so it never falls to the page behind.

## A fix that came with it

CopilotKit runs a frontend tool's handler only when its call has no completed result, and counts the exact content `Forwarded to client` as "not answered yet". The agent sends `TOOL_CALL_RESULT` for `a2g_execute_write`, which the run stream passed on, so for a real agent run the approved write was never executed by the browser; the mock never emitted the tool call, so the ADR 0020 end-to-end tests did not see it. `RunStream` now answers every `a2g_*` tool call with that placeholder (the result is repaired or replaced, the call's arguments are untouched), and `a2g_execute_write` is registered with `followUp: false` so CopilotKit does not start a second run when the handler finishes. The mock chat now emits the same tool call after an approved memory save, so the browser path is tested.

## Not in this change

Automatic suggestions (option B: "You asked for 90 days 4 times. Remember that?") build on this storage and panel: see ADR 0023. Editing an item in place and sharing items between people are out of scope. The deployed IAM for the saved-views table is part of the AWS infrastructure work (ticket #24): the BE Lambda's role on it also needs `dynamodb:DeleteItem` (it already writes and queries it for saved views and the appearance choice).

## Testing

- `backend/agent/tests/test_memory.py`: the guard against the shared cases, categories, the remember parser (only an imperative at the start; a question is ordinary chat), a rejected approval saving nothing and an edit being re-checked, the prompt note (quoted data, invalid items dropped), the run ending at the card, a record fact refused without a model call, items reaching the system prompt.
- `backend/lambdas/api/tests/test_agent_memory.py`: the guard against the same cases, the owner-keyed store (round trip, owner only, duplicates, cap, delete, clear leaves other preferences, store down is `Unavailable`), items kept out of saved views, every run carrying the caller's items, the resume path accepting the new kind. `tests/api/test_agent_memory.py` proves the same through AppSync on the local stack.
- `frontend/src/lib/data/agent-memory.test.ts`, `run-stream.test.ts`: the mirrored guard, the mock store and chat flow, AppSync operations with no owner, the interrupt allow-list, the browser-tool placeholder.
- `frontend/e2e/agent-memory.spec.ts` on the iPad and MacBook projects (panel and docked): remember on approval and review it, delete, reject, edit before approving, a record fact refused, clear-all behind a confirmation, Esc and focus. The chat visual baselines whose header changed were regenerated.
